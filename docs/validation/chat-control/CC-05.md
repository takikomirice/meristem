# CC-05 工程表・報告と直列Git

実施日: 2026-11-16（日本時間）。**実装・ローカルbare remote fixtureの検証を完了。計画の9項目を確認した。**

## 有効化と工程表

専用configの `mcp.scope` に `plan: true`、`assignments: []` を指定する。既存の `fixture: true / planPath / repositoryId / repositoryPath / branchScope` は維持し、`branchScope` に計画の `integration_branch` を含める。`repositoryPath` と計画のrepositoryは同じ実worktree rootに限定する。従来fixtureはplanを省略すれば互換動作する。通常導入用installerではない。

`worktrees_root` は事前に作成した、元repository外の専用ディレクトリを絶対パスで指定する。originが設定された実Git repositoryが必要。専用integration branchは未使用の非保護branchにする。制御側はmain/masterを拒否し、branch作成を `git worktree add -b` に限定する。GitHub等の追加の保護規則は自動推測しない。

fetch URLとpush URLをそれぞれ一つ固定し、worktree固有設定も照合する。候補到達は固定push URLへ問い合わせる。`url.*.insteadOf / pushInsteadOf` による書換えはplan modeでは未対応として拒否する。設定を自動修正せず、直接URLを持つ専用試験repoを使用する。

```yaml
schema_version: 1
run:
  repository: 'C:/work/project'
  worktrees_root: 'C:/work/managed-trees'
  integration_branch: cc05-review
  max_parallel: 1
tasks:
  - id: A
    depends_on: []
    scope: [src, test]
    conflicts_with: [lockfile]
    agent: {model: example-model, effort: low}
    continuation: {mode: new}
    completion: [unit]
  - id: B
    depends_on: [A]
    scope: [docs]
    conflicts_with: []
    agent: {model: example-model, effort: low}
    continuation: {mode: new}
    completion: [docs-check]
```

上記YAMLをMarkdownの `<!-- chat-control:plan:start -->` と `<!-- chat-control:plan:end -->` の間に置く（コードフェンスは含めない）。別に `<!-- chat-control:progress:start -->` と `<!-- chat-control:progress:end -->` を用意する。自由記述は両領域の外に残す。

- schemaは未知キーを拒否する。scopeはrepo相対のファイル／ディレクトリprefix、globではない。`..`、絶対パス、`.git`等は拒否する。conflicts_withは共有資源名。completionは必須検証の名前の配列。
- continuationの省略は `{mode: new}`。`{mode: same, after: A}` はAが直接依存にある場合だけ指定できる。`parent_decides` は親の明示判断まで割当を保留する。
- file上限256 KiB、task上限128。YAML 1.2の単一文書、重複キー・custom tag・aliasを拒否する（alias上限0）。yaml 2.8.2を固定し、既存のzodとNode標準APIを使用する。
- 計画領域hashと全file hashを分離する。生成欄や自由記述の変更だけでは計画版を変えない。計画変更を検知すると次の配送を凍結し、元snapshotをDBに保持する。

## 親と子の契約

人のRunPermit確認後、親の `create_worker(taskId)` が新しいbranch/worktreeを作る。配置は `worktrees_root/runId/integration` と `worktrees_root/runId/taskId-attemptId`。既存branch・directoryを引き取らず、元workspaceのdirty状態は変更しない。CC-05の配送は直列。schemaはmax_parallel 1/2を認識するが、子2件の並列配送はCC-06まで有効にしない。

`get_status` は現在attemptの `git: {taskId, attemptId, cwd, branch, baseSha, scopeBaseSha}` と、親向け `plan` の状態・SHA要約を返す。検証本文は報告ページから取得し、全工程分を状態応答へ重複しない。子のreportは以下を必須とする。

```json
{
  "task_id": "A", "worker_id": "A", "attempt_id": "実attempt ID",
  "actor_id": "実thread ID", "status": "completed",
  "base_sha": "割当の完全SHA", "candidate_sha": "成果commitの完全SHA",
  "branch": "割当branch",
  "push_result": {"status": "pushed", "remote": "origin", "branch": "割当branch"},
  "summary": "変更の要約",
  "checks": [{"name": "unit", "command": "npm test", "result": "passed", "exit_code": 0, "evidence_refs": ["検証記録への参照"]}],
  "remaining": []
}
```

statusは `completed / failed / needs_input`、push_result.statusは `pushed / failed / not_attempted`。candidate_shaは未作成時null可。質問はstatus=needs_inputで `question` を加え、CC-04のanswer_requestで扱う。actor_idはthread IDを表し、本文を身元証明には使わない。native検証済みWorkerRefと全IDを別途照合する。

正常turnと報告turnの一致、未解決要求なし、worker後始末完了、実HEAD／branch／clean／base祖先／scope／origin到達、必須checks成功が揃うと `candidate_ready`。push失敗、後からの変更、残存プロセス、不明な終了は保留する。checksのcommandを制御側が自動実行する機能はない。親が成果と証拠を読み、統合後の検証を実行する。

親の `record_decision` はoperation、taskId、evidenceRefsと以下を受け付け、親turn IDと共に保存する。

| decision | 追加値と条件 |
|---|---|
| retry_same / continue_same | 必要ならsourceTaskId。正常終了・後始末済みの管理worktreeを同履歴の新attemptで使う。別taskの履歴は統合済み直接依存だけ |
| handoff_new | 新しい履歴と新しいworktreeで割り当て直す |
| accept_candidate | candidateShaを固定。依存は解放しない |
| accept_integration | integrationShaとchecks。専用integration worktreeのcleanな実HEAD、候補と先行integrationの祖先関係を再確認して依存を解放 |
| pause | 新規配送とwakeを禁止し、所有workerを停止 |
| finish | 全taskの統合と後始末を確認してrunをcompletedへ |

親は専用integration worktreeで通常merge／fast-forwardと検証を行い、そのSHAをaccept_integrationに渡す。同履歴を使う際も、必要な先行integrationへの追従は親が通常merge／fast-forwardで行う。制御側はreset、force-push、worktree／未コミット変更の削除を行わない。旧attemptの操作を再送して新attemptを起動することもない。

実行baseShaとscope検査のscopeBaseShaを分け、同taskの修正は初回からの累積差分を検査する。別taskへ履歴を渡す場合は再利用HEADと専用integration HEADの一致も要求する。受入前／受入後の追加commitを検査基点へ紛れ込ませない。

`reconcile_plan(expectedFileHash, expectedPlanHash)` は親の照合用。未割当taskの依存・検証名だけ変更でき、run、task ID、scope、agent、continuationや割当済みtaskの変更は新runを要求する。過去snapshotはDBに残す。`write_progress(expectedFileHash)` は生成欄だけを同一directoryのtemp＋renameで更新する。全fileのhashが異なると拒否する。

## 検証と制約

実Git・ローカルbare remoteの直列試験入口:

```powershell
npm run verify
node dist/test/live/serial-git.js --evidence '<未使用の絶対JSONパス>'
```

新A→候補承認→同履歴の修正attempt→統合承認→新B→統合承認を通す。元workspaceをdirtyにした対照を残し、全worktree・branch・DBも自動削除しない。通常testは同じシナリオを実行する。既存native／MCP／terminalの回帰もverifyに含む。

この試験は**実Git＋偽runtimeのfixture**。実Codexの履歴再開・実VS Codeのterminal・実GitHub pushの新規受入ではない。CC-04の対応API表を維持し、未対応承認を自動許可しない。実モデルとGitHub試験は実施しない。CC-06並列／CC-07通常導入は対象外。

再起動後はsnapshot・Git割当・判断を保持し、既存のneeds_reconcileとRunPermit再bindingを要求する。終了不明attemptのworktreeは再利用しない。現在のWorkerRuntimeが保持していない履歴を再起動後に自動復元する機能は追加しない。

## レビューと実装判断

主な変更は `src/plan.ts`（schema・依存・生成欄）、`src/git-evidence.ts`（Git事実）、`src/broker.ts`（PlanControl）、`src/mcp.ts`（認証済みツール接続）、`src/store.ts` と `migrations/005-plan.sql`（永続化）。既存fixtureの契約を保ち、CC-05を明示的に有効にする。

独立した読取専用レビューで、修正attemptへscope外変更を持ち越せる問題と、worktree固有のURL書換えで別remoteを到達証拠にできる問題を実Gitで再現した。累積scope検査、別task引継ぎ時の統合HEAD一致、worktreeごとの実効URL確認と固定push先照合で修正し、失敗する回帰テストから成功を確認した。Critical／保留Minorはない。

自己レビューでは、先頭空白を含む変更パスの扱い、判断記録と依存解放のトランザクション、古いattemptへの配送、停止と候補検証の競合、remote通信中のイベント処理、履歴が大きいときの応答サイズも検証した。remoteのls-remoteは非同期で実行し、確認後にGit状態・計画版・run状態を再確認する。停止が始まっていれば候補承認を保存しない。

計画の未定義部分はcompletionを必須検証名、scopeを相対prefix、conflicts_withを共有資源名として具体化した。既存のcleanなfeature checkoutで作業し、現在branchへのcommit/push方針を維持する。max_parallelのschemaは1/2を認識するがCC-05の配送は直列に限定する。チェック実行や意味判断は親の責任とし、汎用command runnerを追加していない。これらの契約が用途に合わない場合は、対応schemaや後工程を変更する必要がある。

URL書換え・複数URLは未対応として明示拒否するため、その設定を必要とするrepoでは直接URLの専用fixtureを用意する必要がある。別taskへ同じ履歴を渡す場合は親が統合HEADへ追従させる。CC-06／CC-07、実モデル／GUI／GitHub試験は今回のレビュー・受入対象から除外し、完了へ数えない。
