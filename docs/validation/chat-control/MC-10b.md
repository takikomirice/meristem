# MC-10b ワーカー履歴の閲覧と明示再開

2026-11-18（日本時間）。MC-07／08／09bとMC-10aを含む `14795ed` を起点に、専用worktreeとブランチ `feat/mc-10b-history-resume` で実装した。[工程表](../../superpowers/plans/2026-11-17-worker-coordination-evolution.md#mc-10-標準codex履歴への接続と再開前の照合)

## 実装

- VS CodeとCLIの管理接続、および親専用MCPから、完全なWorkerRefに紐付く保存済みスレッドを選択できる。対象の公式VS Code拡張の公開コマンドには、ID指定で読み取り専用の履歴を開く操作が見つからなかった。MC-10aの公式 `thread/read` と `thread/turns/list` を使い、読み取り専用のエディターに概要を表示する。Meristemに会話本文は保存しない。
- 明示再開では最新のattempt、Codexのスレッド・プロバイダー・ターン状態、runの停止世代、権限境界、停止と配送の記録、Gitのブランチ・作業ツリー・依存工程のSHAを照合する。Git HEADは作成時まで固定する。再照合で履歴を確認できなければ以前の履歴準備を失効させる。
- 対象Codex版では旧grantを安全に消去できることが確認できていない。MC-07の方針を引き継ぎ、確認済みworktreeと元スレッドIDを新しいattemptとスレッドに渡す。新しいワーカーの作成と指示の送信は、現行の工程設定とrunの権限上限で別々に実行する。テスト・統合済みの判定には既存のGit証拠を使う。
- 未解決の相談は再起動後の一覧に残り、旧ウィンドウのフォームは失効する。配送不明で親を再承認できない場合も、管理接続から読み取り専用で一覧を確認できる。結果不明の配送記録は保持する。

## 専用VS Codeでの確認

隔離したVS Codeプロファイル、ローカルGit fixture、Windowsのnative gateway、MockCodexを使った。実Codex認証と実モデル送信は使用していない。通常のVS Codeウィンドウや通常プロファイルへの導入はこの試験の対象外。

| 試行 | 観測結果 |
|---|---|
| 履歴の閲覧 | 専用VS Codeの終了を確認して再起動した。停止済みrunから保存されたスレッドを選び、履歴本文をエディターで確認した。閲覧前後でrunのrevision・停止世代・attempt数は同じだった。履歴接続のRPCは初期化・`thread/read`・`thread/turns/list` の3件。 |
| 明示再開の準備 | 別のVS Code再起動で、親の `resume_run` を明示実行した。再開元を選び、対象のスレッドとブランチを確認して「照合して準備」を実行した。成功通知とrevisionの更新を確認し、新しいattemptや新しいターンは発生しなかった。新規attemptへの接続と旧権限を引き継がないことは自動テストで別途確認した。 |

別のCLI試行で `resume-history` に続けて親のMCPから `create_worker` を実行し、同じworktree・branchで新しいattemptとスレッドが待機状態になることを確認した。開始したワーカーのnative停止を確認し、実モデルへの送信は0件だった。

試験の終了時に専用VS Code、relay、gatewayの不在を確認した。元attemptの停止結果は記録されている。実Codexモデルを使った履歴の確認と同一スレッド継続の受入は `not_run`。
