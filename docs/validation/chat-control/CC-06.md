## 並列配送

CC-05の `mcp.scope.plan: true` を使い、工程表の `run.max_parallel: 2` を指定する。scopeが同じ、親子ディレクトリが重なる、または `conflicts_with` の共有資源名が重なる工程は同時に割り当てない。scopeはWindowsの大文字小文字も同一視する。依存は `accept_integration` でのみ解放する。

予約は単一writerのトランザクション内で行い、起動中・idle・回答待ちも枠を占有する。停止確認不能のattemptが残る場合は配送しない。同じ履歴を別工程へ継続する場合も、worktree／担当が生存attemptに占有されていないことを検査する。内部サブエージェントに主担当の権限を与えない。既存の専用host/jobとterminal bindingを再利用する。

一方のタブ閉鎖後、兄弟の現在turnに必要なローカル `report/get_status` の人によるMCP承認は継続できる。新たなGit権限付与や質問への次turn送信は許可しない。全体停止・lease喪失・再起動・明示再開でこの継続対象を失効し、古いフォームからの配送を認めない。

並列なのは子の作業turn。親の変更系MCP操作は一つずつ行い、各操作の前に最新の `run.revision` を取得する。同じ `expectedRevision` でA/Bの作成を一括送信すると一方は拒否される。明確なrevision拒否は最新状態と新operation IDで修正できるが、配送結果が不明な操作は再送しない。

人の承認待ちの間に兄弟が報告するとrevisionが進む。未適用のrevision競合は `stale_revision / not_applied` として元の子へ返す。その場合だけ最新状態と新operation IDで報告し直せる。呼出し元や認可の不一致、結果不明の配送は、この再送可能な分類に含めない。

RunPermit確認後の `start_run` は、bindingを要求した初回と**同じoperation ID**で再提示して消費する。それまでは `get_status` も許可されない。通常の変更操作で使う新operation IDと混同しない。

## 親による統合

子は割り当てbranchにcommit/pushし、構造化reportを保存する。正常turn、要求の解決、後始末、Gitのclean・HEAD・scope・remote到達を確認して `accept_candidate` する。これは候補の固定で、依存の解放ではない。

並列計画では次の順番で進める。Git操作と検証コマンドの実行・意味上の判断は親が行う。

1. `record_decision` の `prepare_integration` に `taskId` と `inputCandidateShas`（1〜2件）を渡す。対象は承認済み候補。専用integration worktreeがcleanで、HEADが受入済みのbaseに一致することを確認し、baseと候補を保存する。
2. そのworktreeで固定したSHAを順次mergeする。子branchへ変更を加えない。実装の前提が衝突した場合は意図を読んで解消し、解消内容をcommitする。人にしか判断できない仕様矛盾は質問へ戻す。
3. 選択した全工程と既に統合済みの工程のcompletion、および `integration` という名前の統合テストを実行する。各checkは `checked_sha` に**検証した最終HEAD**を指定する。commit後にSHAが変わったら再検証する。
4. `accept_integration` にanchorの `taskId`、`integrationSha`、`checks` を渡す。選択候補の再照合、base／全入力／先行統合の祖先関係、clean状態、検証SHAを確認し、両工程の受入を一つのトランザクションで保存する。

保存する統合証拠は `inputCandidateShas / resultSha / checks / acceptedByParentTurnId`。checkは親からの検証記録であり、brokerがコマンドを再実行した証拠ではない。親は実際のコマンド結果を `evidence_refs` に記録する。

`record_decision.evidenceRefs` は英数字・ハイフン・アンダースコアの識別子（例 `check_A`）であり、check内の自由な `evidence_refs`（例 `check:A`）とは形式が異なる。

`cancel_integration` は準備中の統合予約だけを解除する。未コミット変更・merge中のindex・branch・候補は消さない。dirty状態や受入外HEADが残る限り、次の配送／統合準備は拒否される。親がGitの状態を解決した後に修正attemptや再準備へ進める。

`max_parallel: 1` の既存の直列受入は維持する。SHAを明記したcheckは任意で追加できる。新規依存、DB migration、子への直接terminal入力は追加しない。

## Git権限の正式承認

人の承認画面では担当、要求内容、依頼理由、対象パス、有効期間を先に表示する。理由・報告要約は「担当の説明」と明示し、許可内容そのものは検証済みの権限から生成する。同じパスがwire形式の複数フィールドに現れても重複表示しない。permissionsは同じturnの後続コマンドにも適用され、対象内の作成・変更・削除を含むことを示す。commandは実行コマンド全文と1回限りの範囲を示す。UUID・request ID・hash・form generationは末尾の照合情報へまとめる。MCPのreport承認と成果物の採用は区別する。表示の変更でhash照合や元request IDへの配送は変えない。

工程表で固定したGit common-dir、割当worktreeから照合したその配下のGitディレクトリ、絶対パスで指定され実体がbare repositoryと確認できたpush先だけを承認対象にする。管理領域と同じパス、その親・子パスは拒否する。`item/commandExecution/requestApproval` は追加filesystem権限がこの範囲に収まる通常commandだけ、`item/permissions/requestApproval` は要求されたfilesystem権限をそのturn限りで返す。人の回答は既存の親elicitationまたは補助拡張modalから元request IDへ配送する。親AIから承認値を渡すことはできない。

linked worktreeでは共通 `.git` への許可だけでは不十分で、解決されたworktree固有のGitディレクトリも明示する。[固定Codex版のpermissions実装](https://github.com/openai/codex/blob/rust-v0.169.0-alpha.11.1/codex-rs/protocol/src/permissions.rs#L1520-L1535) と実機でのindex.lock拒否を照合した。ACLの直接編集やsandbox全体の解除は行わない。

登録時の実体パスを固定し、許可直前にも照合する。環境IDを含む要求は、起動応答で確認した単一のlocal環境と割当cwdに一致するものだけを扱う。commandの変更可能な別名パス、任意ディレクトリ、network承認・policy変更、session許可、writeStdin、広いsandbox解除は扱わない。permissionsの拒否／取消は空の権限を返し、要求を解決する。file changeは変更内容を安全に照合する経路がないため未対応のまま保留する。OS承認・ログイン・公式reviewerを代理しない。

公式型は固定Codexの `app-server generate-ts` で照合した。固定版では `request_permissions_tool`／`exec_permission_approvals` が既定で無効のため、Git承認対象を持つ子のthread設定だけで有効にする。sandboxと管理領域のdenyは維持し、起動時に権限を付与しない。実Git操作の受入は下記の実モデル試験で別に記録する。

固定版のelevated方式による実機試行では、3パスのturn許可が子へ返り、sandboxのwrite ACE付与ログも記録された後に、`index.lock` 作成が拒否された。起動前の隔離確認とthreadのfilesystem helperが先に付けた、作業場所等に対応するcapability SIDへの明示Denyが残っていた。固定ソースは新しいGit rootのSIDへAllowを付けるが、以前のDenyを同期して除去していない。これはログ・ACL・ソースが支持する原因であり、終了済みコマンドの実tokenは採取していない。ACLを直接変更して解決したとは扱わない。

`runtime.windowsSandbox` は省略時に既存のCodex設定を継承する。`elevated` または `mxc` を明示した場合、起動前の隔離確認と子のthread/start・resumeに同じ公式設定を渡す。[固定版のMXC方式](https://github.com/openai/codex/blob/rust-v0.169.0-alpha.11.1/codex-rs/mxc-sandbox/README.md) はホストACLを書き換えずcanonical permission profileを適用する。利用できない場合の自動fallbackはなく、管理領域のdenyが確認できなければworkerを開始しない。既存の人によるGit権限承認は必要なままである。MXCは対応OSとnative deny能力が必要で、hardlinkやvolume alias、子孫プロセス寿命に方式固有の制約がある。一般のWindows環境での互換性は今回のPCの結果から推定しない。

実機runnerでは `prepare --windows-sandbox mxc` で子だけに明示指定でき、選択をsessionに記録する。認証homeの設定や通常の親windowの方式は変更しない。無推論のcanary試験で、作業領域のread/write成功、管理領域のread/write拒否、未許可のGit書込み拒否を確認した。Git承認後の成功と停止の実機受入は下記に記録する。
