# MC-06: 人が承認する増員とN件の統合

2026-11-17着手、2026-11-18最終受入。起点`f980879`、作業ブランチ`docs/worker-coordination-plan`。[計画](../../superpowers/plans/2026-11-17-worker-coordination-evolution.md)のMC-06を対象とする。MC-07以降の仕様適用、実モデル・実UI受入は行わない。

## 実装と互換性

- 版1の希望人数1〜2は維持し、版2は1〜128を読む。希望人数と同runの承認上限を分離し、未承認時は2。`Decision.requestedMaximum`をproposalHashに含め、現行plan・相談・フォームを照合した信頼済み人用callbackだけが承認を保存する。フォームに人数・タスクID・工程表のmodel／effortを表示する。人数以外の追加権限は付与しない。
- 新しい増員提案は同runの未回答の旧提案をsupersedeする。自由記述は未承認の修正案、無回答は未承認のまま。同runの承認範囲内での交代は再確認しない。別run、自己承認、旧form、古いplan、上限の直接書換えを拒否する。旧DBのpayloadなし承認記録は読めるが実行枠を拡張しない。
- 単一writerでruntime起動前に枠を予約する。starting・stopping・unknownを計上し、保留・退役は停止確認後だけ枠を解放する。scope・共有lock・worktree予約、owner／epoch／attempt、operation ID／revision、停止・wakeのフェンスを維持する。
- MCP fixture登録・候補配列を128件まで扱い、並列設定の`> 1`と実際の複数入力の両方を判定し、逐次実行で蓄積した複数候補も最終SHA検証の対象にした。全入力とbaseを固定し、候補のremote照合後に全ローカルpinを再確認する既存Git検証を再利用する。既統合・追加completionとintegrationを最終SHAで確認してから一括受入する。
- 必須チェックが32件を超える場合は`record_integration_checks`を使う。1回32件と既存frameを維持し、固定した同じ最終SHAへ最大4097件を集約する。重複名・別SHA・失敗・未実施は受け入れない。SHA変更は明示取消・再準備を必要とし、Git成果を削除しない。
- native statusを最大4件・byte上限付きでページ化し、個別attempt照合と拡張／CLIのページ取得を接続した。MCPとnativeの公式要求一覧もページ化した。nativeの262144 bytesとbroker stdoutの200000 bytesを維持し、状態応答は全セクション合計も18万bytes以内に収める。DB migration・新規依存はない。
