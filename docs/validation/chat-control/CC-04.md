# CC-04 質問と正式な人の承認

実施日: 2026-11-16（日本時間）。**対応APIの専用fixture受入を完了。計画の6項目を検証済み。**

## 実装と対応範囲

- 構造化質問は親の `get_status` に表示し、`answer_request` から元JSON-RPC ID・質問IDに回答する。owner/epoch、attempt、turn、停止状態を照合する。
- 自然文の質問は子が `report.question` に明記する。元turnの正常終了を確認してから、質問ID `reply` の回答を同履歴の次turnへ送る。未送信と確定した失敗だけ再試行可能。不明配送は再送しない。質問の報告と、過去turnの最終報告は現在turnの成果に数えない。
- 対応するローカルmeristem承認は、親の `answer_request`（answerなし）から公式SDKの `elicitation/create` を表示する。人の回答は公開ツール引数にせず、実親App Server直下・固定Node/MCP入口のnative検証を通る内部経路へ返す。人のresponse用ツールは公開しない。
- 親クライアントが非対応、timeout、切断の場合は元要求を保留する。補助拡張の専用modalを代替経路とする。要求内容・cwd・WorkerRef・turn・元ID・hash・フォーム世代を表示する。
- 再表示で世代を更新し、古いフォーム、二重回答、期限切れ、停止・中断後の回答を拒否する。許可・拒否・要求取消は人の明示回答だけで配送する。modalを閉じただけでは回答しない。回答送信後も元の `serverRequest/resolved` を待つ。
- `requests`監査表には識別子・種類・hash・世代・期限・状態のみ保存し、元RPCの要求本文や認証payloadを保存しない。migration 004で既存表へ列を追加する。再起動時に未回答フォームを失効し、送信済み未解決の記録は保持する。

## API対応表

以下はCC-04受入時点の表。CC-06では固定したGit metadata／検証済みローカルbare remoteに限るcommand・permissionsの人による承認を追加した。現在の制約と検証は[CC-06](CC-06.md)を参照。

| API / 状況 | 対応 | 自動検証 | CC-04実機 |
|---|---|---|---|
| `item/tool/requestUserInput`、相関済み・非秘密 | 元RPCへの回答 | 元ID・回答・解決通知・正常終了 | fixture検証のみ（実機の質問は下記経路） |
| `report.question` で終了した自然文質問 | 同履歴の次turn | turn終了待ち・未送信再試行・履歴維持 | acceptance-03で成果ファイル・最終報告まで確認 |
| ローカルmeristemのreport/get_statusの空フォーム | 親の正式elicitation、専用modal | SDK往復・親身元・hash/世代・一回限り | 03でmodal許可、05/06で正式フォームAccept/Deny/Cancel・回答前停止 |
| command/file/permissions、connector/app、その他elicitation | unsupported、元要求を保留 | API別拒否・代理回答なし | 対応完了に数えない |
| 認証・OS承認・公式reviewer | 代理しない | 分類・保留 | 人が専用homeのログイン・Windows設定を実施。配送の合格ではない |
| turnId=null、相関不明、秘密の質問 | unsupported、元要求を保留 | 拒否・停止まで保持 | 対応完了に数えない |

自然文の自動推測は行わない。子が `report.question` を使用する契約で、直接CLI入力やTUI操作は提供しない。`acceptForSession` を別attemptへ持ち越す経路も提供しない。

## 実機記録

入口は `test/live/approval-roundtrip.ts`。各試行は専用fixture・専用認証home・親子合計最大8turn。親送信と子指示は送信前に枠を記録する。statusとevidence取得はモデルを呼ばず、人のUI判断や合格を推定しない。

- acceptance-01: 専用homeの正式ログインとWindowsセットアップを人が実施。設定復元済み。
- acceptance-02: 親3turn、子指示0。人のrun binding後、worker起動が結果不明で停止。実行中の誤った再buildも発生したため合格には数えない。設定復元済み。原因を単一に断定しない。
- preflight-01: 実CLIで無推論のroot thread作成・分離・停止・host消滅を確認。これは承認往復の受入ではない。
- acceptance-03: 親5turn・子2turn。人が補助modalで2回許可し、元要求の解決、質問報告、同履歴の次turn、成果ファイル `CC04_JSON_CONFIRMED`、最終報告、正常終了・native job emptyを確認。途中の親の構文エラーは未送信を確認して訂正した。設定復元済み。
- acceptance-04: 親3turn・子1turn。親の正式フォーム（内容・cwd・元ID・hash・世代、Accept/Deny/Cancel）を表示し、人がAcceptしたがnative許可メソッドの追加漏れで子へ届かなかった。要求保留を確認し、停止・設定復元。あわせてフォーム表示によるrevision更新も回帰テストで再現し修正。失敗試行として保持する。

- acceptance-05: 修正版で親の正式フォームからAcceptとDenyを配送。各元要求の解決、Acceptの報告保存、Denyの報告不保存を確認。親5turn・子2turn。ユーザーの明示委任によりbindingは正式CLIから登録した。子モデルが個々の承認待ち／拒否後に終了したため、後続ケースは別attempt／試行に分けた。設定復元済み。

- acceptance-06: 親5turn・子2turn。人の正式フォームCancel後に元要求が解決し、報告不保存。別attemptで元要求と親フォームを開いたまま公式CLIで停止し、要求cancelled・報告不保存・native job emptyを確認。設定復元済み。

実機証跡は [CC-04.acceptance.evidence.json](CC-04.acceptance.evidence.json)。失敗試行を含む親21turn・子7turnを記録し、各試行の親子合計は承認枠8以内。監視のモデル要求は0。新turnの履歴入力まで0とは主張しない。

受入は上記の対応範囲に限定する。構造化質問の元RPC経路はfixtureで確認し、実機では明示的なreport.questionを使用した。未対応の権限・connector・認証を代理する経路は追加していない。実モデルが承認待ちや拒否後にturnを終える場合があり、連続動作の一般的な安定性保証やCC-05以降の完了には広げない。
