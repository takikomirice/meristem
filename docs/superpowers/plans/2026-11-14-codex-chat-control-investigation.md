# Codex独立チャット間制御の調査計画

作成日: 2026-11-14（日本時間）

> 本書は調査の計画であり、実証結果・製品の実装計画ではない。今回行うのは本書の作成まで。調査実行の依頼を受けるまでは、モデル呼出し、試験コードの作成、プラグイン導入、設定変更、動作中のチャットへの送信・中断を行わない。

**目的:** 普段のWindows＋VS CodeのCodex拡張の使用感を保ち、ある独立チャットから別の独立チャットを観測・作成・指示・中断し、モデルと推論強度を指定できるかを、方法と制約を含めて判定する。

**調査方針:** 公式の接続方法を先に調べ、必要な場合だけMCP・ローカル制御プログラム・通信中継を評価する。既存Meristemの接続部品は参考にするが、専用GUIや工程管理エンジンの継続開発を前提にしない。

**対象環境:** Windows、現在インストールされたVS Code/Codex拡張と実際に起動されるCodex実行ファイル。Node.js/TypeScriptまたはPowerShell等の導入済み手段で最小試験を行う。版は調査開始時に固定・記録する。

## 1. この調査で固定する要求

- ユーザーは既に各工程の中でサブエージェントを利用している。調査対象は、その外側で人間が行っている「工程の依頼→報告確認→修正依頼または次工程の起動」のチャット間制御である。
- 「親」「子」は担当関係を表す。対象は工程ごとの独立チャットであり、標準サブエージェントの作成成功を独立チャット制御の成功に置き換えない。
- 第一希望は、普段のCodex拡張内の独立チャットを親にすること。CLIへの移行、自作チャット画面への移行は合意済みと扱わない。
- 工程表・完了条件・モデル・推論強度はMarkdownとスキルで扱う構想。今回、それらの製品機能は実装しない。
- Q4のモデル・推論強度は、指示を受け取った宛先チャットが実行に使う設定を指す。親自身のモデル変更や、表示上の選択変更だけでは達成としない。
- ①〜④が中心。追加調査は、それらを安全に連続利用できるか判断する基盤事項に限定する。

| ID | 調査する要求 | 必要な実証 |
|---|---|---|
| Q1 | 他チャットの状態を観測できるか | 対象IDに対応した実行中・応答終了・失敗・中断・承認待ち・入力待ち・状態不明の区別。取得できない状態は明記 |
| Q2 | 新しいチャットを作れるか | 一意なID、独立した履歴、指定した作業場所。拡張の一覧・画面に表示できるかも別途確認 |
| Q3 | 別チャットへ指示して実行させ、途中停止できるか | 指定した相手だけが実行。同じ相手への修正依頼と、新しい相手への引継ぎ。中断後に管理対象の作業が止まること |
| Q4 | 指示時にモデル・推論強度を指定できるか | 利用可能な組合せの取得、開始時・次ターン時の指定、要求値と有効値の照合。実行中の変更可否は別判定 |

## 2. 対象を混同しないための比較軸

次の対象を別々に判定する。Aの成功が第一希望を満たす。B/Cだけの成功を「普段の拡張チャットを操作できた」と報告しない。

| 対象 | 説明 | 必要な確認 |
|---|---|---|
| A: 拡張が所有する既存チャット | 試験用プロファイルで人が通常操作により作成した独立チャット | 既存の履歴・表示・人の入力・停止操作を維持して外から制御できるか |
| B: 外部作成後に拡張で開くチャット | 制御プログラムが作成し、拡張の通常画面で開く独立チャット | 再読込みの要否、表示の同期、接続の引継ぎ、同時書込みの競合 |
| C: 外部でのみ管理するチャット | 自分たちが起動したApp Server等の独立チャット | API機能の比較基準。拡張の親への報告配送は別試験 |

経路は「公式API/公開コマンド→MCPからの接続→実行ファイル差替え等の通信中継」の順で調べる。通信中継が開発用設定に依存する場合は、公式サポートと同列に扱わず、Windows対応・更新耐性・元に戻す方法を判定する。権限迂回や拡張本体の無断改変を必要とする経路は採用しない。

## 3. 調査開始前に分かっていることと、未確認事項

以下は資料・コードの読取り結果であり、今回のチャット間実機試験の成功ではない。

- [App Server公式資料](https://developers.openai.com/codex/app-server)には会話・ターンの操作、状態通知、中断、モデル・推論強度の指定がある。拡張が所有する接続へ外から到達できることまでは示さない。
- [MCP公式資料](https://developers.openai.com/codex/mcp)にはIDE拡張からの接続とツールのタイムアウト設定がある。MCP通知だけで終了済みの親が推論を再開するとは仮定しない。
- 手元の拡張 `openai.chatgpt-26.1111.21308-win32-x64` のmanifestに `chatgpt.cliExecutable` が存在し、開発専用と説明されていた。設定を変更した試験は行っていない。調査開始時に実際の導入版を再確認する。
- [cross-agent MCP](https://github.com/whooperlove/cross-agent_mcp)は既存パネルへの中継方式を説明する第三者実装の候補。README上の説明をWindowsでの動作実績として扱わない。

## 4. 実行環境・成果物・証拠

後日の調査実行時に、次の範囲へ試験と記録を限定する。

| 場所 | 用途 |
|---|---|
| `.local/chat-control/<試験ID>/` | 破棄可能な試験用リポジトリ、試験用プロファイル、設定退避、非公開ログ |
| `spikes/chat-control/` | 必要と判明した最小試験コードのみ。製品実装へ自動昇格しない |
| `docs/validation/chat-control/report.md` | 最終判定、条件、非対応、未確認、再現手順 |
| `docs/validation/chat-control/capabilities.json` | Q1〜Q4と基盤項目を対象A/B/C・経路・版ごとに記録 |
| `docs/validation/chat-control/evidence/` | 秘密情報を除いた要求・応答・状態遷移・必要な画面証拠 |

各証拠に試験ID、時刻、版、対象種別、親/子のthread ID、turn ID、操作ID、作業場所、要求設定と観測値、結果を含める。認証情報・token・生の環境変数・実利用チャット本文を公開証拠へ含めない。IDは必要に応じ一貫した別名に置き換え、相関を保持する。

## 5. 調査手順

### R0: 版・接続口・所有関係を固定する（読取りから開始）

- [ ] OS、VS Code、Codex拡張、実起動CLI、Node、認証方式、利用可能なモデル/推論強度、適用ポリシーを記録する。PATH上のCLIだけで拡張同梱版を判断しない。
- [ ] 公式資料、ローカルmanifest・ソース、実CLIから生成可能なprotocol schemaを照合し、公開API・実験的API・開発用設定・非公開依存を分ける。
- [ ] A/B/CそれぞれのApp Server所有者、接続方法、thread IDの入手方法、単一書込み制約を図示する。接続確認のためのresumeが状態を変える場合も記録する。
- [ ] 試験用プロファイルへの変更項目と復元手順を確定する。起動・停止権限を対象プロセスに限定できなければ実機試験を始めない。

**成果:** 経路別の試験可否と、実行する最小試験一覧。必要な入口がない経路は、その根拠を残して打ち切れる。

### R1: Q1 状態観測とチャットの正確な識別

- [ ] 親P、子A、子B、対照Dを試験用に用意し、可能なら別ウィンドウにも対照を置く。名称・最新更新・前面タブだけを宛先に使わず、IDを使う。
- [ ] 短い実行、正常な応答終了、意図的な失敗、中断、承認/入力待ちを作り、通知と読取りAPIで何を識別できるか記録する。履歴の存在、無通信、プロセス終了、idleを工程成功と同一視しない。
- [ ] 「モデルが返答した」「実行コマンドが終了した」「依頼の完了条件を満たした」「子が完了報告を送った」を分ける。生の内部思考を取得できる前提にはしない。
- [ ] 観測だけで新しいモデルturnやファイル変更が発生しないか、他チャットのイベントが混入しないか確認する。

**合格条件:** 得られる状態と不明状態を対象ID付きで区別できる。観測による副作用がある経路はその条件を明示し、「受動監視可能」としない。

### R2: Q2 独立チャットの作成と通常画面への表示

- [ ] 指定cwdと一意なマーカーを持つA/Bを作成し、異なるthread IDと独立履歴を確認する。新規作成、既存会話の再開、履歴分岐を区別する。
- [ ] 拡張の一覧への出現、開く操作、送信/実行の表示、再接続後の表示を確認する。「バックエンドで作成できる」と「普段のチャット画面で扱える」を別に記録する。
- [ ] 作成応答が届かない場合、作成済み会話の存在を照合できるか確認する。成功不明のまま自動で別チャットを増やさない。

**合格条件:** 一意なIDと作業場所を確認し、通常画面で扱える条件または画面連携の非対応を記録できる。

### R3: Q3 指示・修正依頼・中断

- [ ] 親からAへ、試験リポジトリ内の専用ファイルにマーカーを1回だけ書く固定指示を送る。Aだけの履歴・実イベント・ファイルで実行を確認し、B/Dに影響がないことを確認する。
- [ ] 完了後のAへ修正依頼を送り、同じIDと履歴で続くことを確認する。別のBへ渡す場合は成果物と前提を明示し、会話を替えても途中変更を消さない。
- [ ] 実行中の追加指示、通常の次ターン、親による中断、人による通常パネルの停止を分けて試す。人の入力と自動送信が重なった場合の順番・拒否・待機を確認する。
- [ ] 待機を含む管理対象の試験コマンドを途中停止し、中断通知だけでなくプロセスとその後のマーカー書込みが止まることを確認する。管理対象外の対照プロセスは停止しない。

**合格条件:** 宛先・履歴・実行結果が一致し、中断の有効範囲が分かる。「中断要求を受け付けた」だけでは停止済みにしない。外部送信中もパネルの停止が効くかを独立に判定する。

### R4: Q4 モデル・推論強度の指定と実効値

- [ ] モデル一覧と各モデルの対応推論強度を取得し、利用可能な組合せから短い試験を選ぶ。資料の例や固定モデル名を利用可能性の証拠にしない。
- [ ] 新規チャット開始と同じチャットの次ターンで指定する。再開時の維持/上書きと、次回以降の既定値への影響を確認する。
- [ ] 要求値、返却された有効設定、実ターンに対応するイベント、通常UIの表示を照合する。要求が受理されただけで実効値の確認済みにせず、推論時間から強度を推測しない。
- [ ] 不正モデル・非対応強度を拒否できるか、黙って別設定へ切り替わらないか確認する。実行中の変更は「その場で変更」「次ターンのみ」「拒否」を区別する。

**合格条件:** 操作ごとの指定可能範囲と確認可能な実効値を記録できる。外部指定と画面表示が食い違う場合は未解決事項にする。

### R5: 親への報告と、応答終了後の自動続行（最優先の基盤事項）

- [ ] 子の報告を受け取る経路を、親がツールで待機中、親が実行中、親が最終応答を返した後、パネル非表示/閉鎖時で分けて試す。
- [ ] 「報告が保存された」「パネルに表示された」「親のモデルturnが開始した」「親が次の子を起動した」を別々に確認する。MCP通知やツールの結果配送だけで親が自動再開したとしない。
- [ ] 最小の2工程で、子Aの固定成果物→報告→親の確認→子B起動→Bの成果物確認まで、人が途中で指示を入力せずに通す。子Aの失敗時はBを起動しない。
- [ ] ツール待機の期限・取消、通知の重複/遅延、親の終了直前の報告を試す。待機期限切れを作業失敗や完了に置き換えない。無限ポーリングや無制限の親再起動を必要としないか記録する。

**合格条件:** 普段の拡張チャットを親にしたA経路で、どの親の状態から人手なしに次工程へ進めるか実証できる。親の最終応答後は進めない場合、待機中だけの連続運転と明記する。C経路で親を制御できてもAの合格にはしない。

### R6: 承認・停止・二重実行・復旧の最小確認

- [ ] 子の承認要求/自由入力/認証要求を区別して親側へ知らせられるか調べる。一括許可/拒否の操作可否はQ1〜Q4と別に判定し、試験用の既知要求だけで確認する。AI判断の代行と人による集約操作を混同しない。
- [ ] 親が応答不能でも操作できる全体停止経路を確認する。「次の子を起動しない」と「実行中を中断」を分け、停止後に遅れて届いた報告で再開しないことを確認する。
- [ ] 送信後の応答喪失、切断、重複報告を注入し、同一操作の実行回数を専用マーカーで照合する。不明結果を即再送しない。読取りで照合できなければ停止状態を残す。
- [ ] MCP/制御プロセス再起動と試験用VS Codeの再読込み後、同じ会話ID・作業場所・進捗から再開できるか確認する。古い状態で二重起動・別チャット誤送信・既存変更の破棄をしない。
- [ ] 文脈不足、利用上限、通信障害、人の中断を別に分類する。実利用枠を使い切る試験はせず、必要なら模擬エラーで確認し実制限時は未確認とする。
- [ ] Markdownの進捗更新は親に集約し、実行役に最低限残すID・未解決操作・停止状態を整理する。保存方法は必要な競合/復旧条件から選び、専用DBを前提にしない。

**合格条件:** 既知の成功と不明結果を区別し、少なくとも安全に止まり、保存状態を調べてから再開できる。完全な自動復旧やOS再起動対応を実証なしで主張しない。

### R7: 既存実装・導入形態を比較し、採否を決める

- [ ] [cross-agent_mcp](https://github.com/whooperlove/cross-agent_mcp)、[agent-runtime](https://github.com/FBisca/agent-runtime)等の候補を一次資料と必要最小限のソースで評価する。対象のcommit、ライセンス、Windows対応、必要ランタイム、親の入口、Q1〜Q4/R5/R6の対応、認証、設定変更、保守負担を一覧化する。
- [ ] 子の通常チャット内で既存スキル・サブエージェントを使えるかは互換性項目として確認する。それらを外側の独立チャット制御の代替案にすり替えない。
- [ ] MCP直接接続、将来のCodexプラグイン化、VS Code拡張との違いを整理する。プラグインの対応画面・配布形態はその時点の公式資料で確認し、パッケージ化が自動続行を解決するとは扱わない。
- [ ] 試験で変更した設定を復元し、試験所有のプロセスを停止する。普段のCodexの送信・停止・モデル選択が引き続き使えることを確認する。証拠・fixtureは保持する。
- [ ] 結果表と推奨する最小構成を作成する。既存Meristemは「再利用候補」「当面不要」「今回未判断」に分けるだけに留め、削除・移行・継続実装は行わない。

**成果:** 採用可能な既存品、追加が必要な小さな部品、第一希望では実現できない部分を根拠付きで示す。

## 6. 判定方法と出口

判定は `確認済み` / `条件付きで確認済み` / `非対応を確認` / `未確認` の4種類とし、資料のみ・静的コード・模擬試験・実Codex・実VS Codeを証拠欄で分ける。APIの存在から実画面での成功を推定しない。

| 項目 | 対象A | 対象B | 対象C | 版・経路・証拠・制約 |
|---|---|---|---|---|
| Q1 状態観測 | 未確認 | 未確認 | 未確認 | 調査時に記入 |
| Q2 新規作成・画面表示 | 未確認 | 未確認 | 未確認 | 同上 |
| Q3 指示・実行・中断 | 未確認 | 未確認 | 未確認 | 同上 |
| Q4 モデル・推論強度 | 未確認 | 未確認 | 未確認 | 同上 |
| R5 報告後の親の自動続行 | 未確認 | 未確認 | 未確認 | 親待機中/最終応答後を区別 |
| R6 承認待ち通知・全体停止・復旧 | 未確認 | 未確認 | 未確認 | 集約回答の可否も別記 |

最終結論は次のどれかを選び、成功した一部の経路で全体を断定しない。

1. **第一希望で成立:** 拡張の親チャットから独立した子を制御でき、人手なしの2工程接続、設定指定、停止まで確認できた。待機や再起動の条件を明記する。
2. **条件付き成立:** 親が待機中だけ続行可能、通信中継が必要、UI表示に再読込みが必要等。使用感の変化と維持費を示す。
3. **外部所有チャットのみ成立:** 基本APIは利用できるが既存拡張の親へつながらない。CLI/独自画面を代替採用したことにしない。
4. **現条件では採用困難、または判断材料不足:** 足りない入口・制約・未実施試験を明記する。
