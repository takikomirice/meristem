# Meristem v0.3.0 実装計画

2026-11-19。対象は [製品仕様](../specs/2026-11-19-meristem-v030-design.md)。実装時は v0.2.0 の Coordinator が下の版2工程表を読み、各工程のチェックと統合を担当する。作業手順には `superpowers:executing-plans` を使える。

## この計画の実行環境

- 製品コードの基準はタグ `v0.2.0`・SHA `befafa89ddeb22043155868c340912da9cef3802`。仕様・計画の作業ブランチは `work/v030-design-plan`。実装用 checkout には両文書を含むコミットを取り込み、製品コードの差分が基準どおりであることを確認する。実行中は v0.2.0 のビルド snapshot を別ディレクトリに固定する。新しい入口・枠制御は完成後の受入対象。
- 工程表の絶対パスはこの Windows 開発機向けの予定配置。実装開始時に D:/cursor/meristem-v030-run 下へ、ローカル bare origin、そこからの作業コピー repo、別ディレクトリ worktrees を準備する。通常 checkout の origin を変更しない。別配置なら開始前に下記2パスを確定する。統合ブランチ名が未使用であること、実行時モデルカタログ、対象工程表・Git 範囲・RunPermit を v0.2.0 の手順で照合する。実機試験の送信予算は親子分を事前に決める。[v0.2.0 運用](../../chat-control-reference.ja.md)
- 版2の開発 run は v0.2.0 配布版の専用環境で起動する。導入設定の `prepare.planPath` にこの Markdown の実体を指定し、`install.ps1 -Prepare`、生成した要求で `install.ps1`、固定した親で `start_run`、人の RunPermit 確認、同じ親の `start_run` の順で接続する。版1を前提にする開発シナリオ生成 CLI はこの工程表には使えない。[版2の導入手順](../../releases/INSTALL.ja.md)
- 入口は「Meristem の開始を呼んだチャットが親」。既存会話を選ぶ画面は作らない。P0 の結果で入口別の方式を確定する。試験では候補ごとに別 run を使う。仕様内の20％・1人・60秒は変更可能な設計初期値。

## v0.3.0 の開始と承認

- 人が Meristem に開始を指示したことと、その指示が適用される親・リポジトリ・工程表・権限範囲を信頼できる入口で照合できた場合、その指示を今回の開始許可として記録し、そのまま開始する。開始時に表示する範囲には工程表の版、対象ブランチと Git の送信先、通常の作業で許可する操作、人数上限を含める。
- チャットからの開始で人の操作や対象範囲を照合できない場合は、候補を示して同じ VS Code ウィンドウに「この範囲で開始」を表示する。その操作で許可の記録と開始を一度に行う。CLI では人が直接操作する端末の制御経路で同じ判断を受け付ける。チャットの本文や Coordinator の申告だけから承認記録を作る経路は拒否する。
- 承認を求める前に、実行環境、選択した親方式、Worker の隔離環境、リポジトリと Git の範囲を診断する。開始・接続の再試行では、同じ run と承認範囲を安全に照合できれば記録済みの許可を使う。送信の結果が不明な場合は照合を待ち、同じ操作を再配送しない。
- 開始時に示した範囲内の Worker 操作と Git 操作は、作業中に再確認せず進める。別の送信先、追加の書き込み先、人数上限の引き上げなど、当初の範囲を広げる場合に、その理由と差分を示して人の判断を受け付ける。VS Code では開始・追加権限の通知と回答を開始元ウィンドウにまとめる。

## 各工程の作業と判定

各工程では該当 fixture を先に追加して旧版で不足を確認し、実装後に同じケースを再実行する。下記の英字名は工程表の completion と一致する。Worker は実行コマンド・結果・候補 SHA を記録する。Coordinator は統合後に同じ必須チェックと `integration`（`npm run verify`）を最終 SHA で確認する。通常プロファイルや有料モデルを使う実機受入は対象と予算を確定した試験環境で行い、記録にアカウント ID、認証値、会話本文を含めない。

### P0　実機の証拠で方式を決める

- [ ] 固定 Codex の版・hash、`codex --help` の `--remote`、`app-server generate-ts` の usage 型、通常の VS Code 拡張の公開操作を記録。実装中のサービスと独立した検証用リポジトリを用意する。
- [ ] VS Code / 公式 CLI × 既存会話で開始 / 同じウィンドウまたは端末で新規管理起動の4通りを試す。CLI 管理起動は所有するローカル App Server へ公式 TUI を接続し、その TUI の会話から開始する。VS Code の管理起動は統合ターミナル内の公式 TUI も候補。P0・P5・P6 の CLI 単独試験は開発用 v0.2.0 Coordinator とは別の Windows 試験機または VM で、VS Code を起動せず実施する。人が入力した会話が指示・報告・次ターンを扱った証跡を取る。
- [ ] `probe` は各構成の起動、呼出元の一意性、並行する無関係な会話、Worker 報告後の同じ thread への wake、入力・未送信下書きとの競合、停止、再接続の観測表。障害・未観測も残す。公式 usage の実読取りはモデルターン0で行い、実際に取得できた窓を記録する。
- [ ] 各入口で人の開始操作をどの情報で確認できるか、起動障害を承認前に診断できるか、開始と追加権限の確認を同じウィンドウまたは端末に提示できるかを記録する。v0.2.0 で必要だった操作と、v0.3.0 の候補で減らせる操作を記録する。
- [ ] `decision` は4通りの結果、操作数、設定への影響、API 依存、採用根拠を `docs/validation/chat-control/v030/parent-matrix.md` に記載。既存会話が失敗して管理起動だけ成功ならユーザーに代替を提示し、対応範囲を決めてから進む。片方の入口の成功で他方を合格にしない。

### P1　共通の親登録・制御接続を実装

- [ ] `src/actors.ts`、`src/contracts.ts`、`src/mcp.ts`、`native/StdioRelay.cs` の固定親登録を、新規 run では最初に検証済みの開始を呼んだ主体に結び付ける。信頼できる入口が確認した人の開始操作と、診断済みの親・工程表・Git・権限範囲を同じ run に記録する。許可の記録から開始までを一つの論理操作とし、同じ開始の再試行は記録済みの run を返す。旧設定の読込みも残す。
- [ ] `src/cli.ts`、`src/wake.ts`、native host に共通の親接続・切断処理を用意。VS Code のウィンドウ、CLI の所有する対話セッションがそれぞれ接続の生存を証明する。古い世代やプロセスを推測して再接続しない。親の停止、再開、承認を Worker が実行できないことを確認する。
- [ ] `binding` と `lifecycle` は `npm run build:native`、`npm run build` 後に `node --test dist/test/actors.test.js dist/test/mcp-native.test.js dist/test/wake.test.js`。検証済みの人の開始操作、モデルだけによる開始許可の記録拒否、範囲変更・他会話の拒否、二重開始、遅延報告と stop の競合、再起動時の許可の照合を試す。

### P2　公式の利用枠を読み取る

- [ ] `src/usage.ts` に取得・正規化をまとめる。対象の認証コンテキストに属する公式応答と通知のみを受ける。窓ごとに残量と reset を返す。通知の欠落項目で既知状態を消さず、通知からの再取得をまとめる。API 未対応・認証不一致・欠測・古い応答の結果型を分ける。
- [ ] `usage` は `npm run build` 後の `node --test dist/test/usage.test.js`。使用済み80→残り20、複数窓、旧単一枠、無関係な別枠、両窓 null、期間のみ null、不正％、通知の順序逆転、アカウント切替、明示拒否→不明→同一アカウントの許可を試す。

### P3　割当と残量ポリシーを結合

- [ ] `src/store.ts` の承認済み人数・Worker 登録、`src/broker.ts` の割当予約、`src/plan.ts` の eligibleTasks を追い、各入口が同じ判定を使う。モデル用の希望人数・承認と、取得時刻付きの残量上限・待機理由を別々に管理。新規 run の設定は開始時に固定し、旧 run の復元は旧既定を使う。
- [ ] `src/cli.ts` と `src/mcp.ts` の状態応答に表示用の窓と実効人数を追加。リセット時や一時障害後はモデルを呼ばず再取得し、待機解除を一度通知する。取得 I/O は取引の外、最終検査と予約は同じ取引で行う。枠低下と予約済み Worker の登録が交差したら二重計上や孤児プロセスが発生しないよう検証する。
- [ ] Worker が通常の保存に必要とする Git 操作を、開始許可に含まれる専用作業ツリー・割当ブランチ・送信先に限定する。既存の Git スコープ照合を再利用し、Coordinator が許可されたコミットと push を追加確認なしで処理できるようにする。操作直前に Worker の割当と対象を照合し、Git 管理領域への任意の書き込みや別ブランチへの操作は拒否する。送信先など許可範囲の拡張は人の判断まで保留する。
- [ ] `admission` は `npm run build` と `node --test dist/test/parallel.test.js dist/test/plan-control.test.js dist/test/git-evidence.test.js`。残り21/20/1/0％、上限2と増員承認、稼働中3→上限1、同時予約、引継ぎ・保留解除、枯渇後の null、自動制限無効、許可済み Git 操作と範囲外への拒否を含める。`migration` は `node --test dist/test/store.test.js` で既存 DB・工程表版1/2の復元と新 run の設定保持を確認。

### P4　通常 VS Code で使う

- [ ] `extension/package.json`・`extension/src/extension.ts` に開始・使用状況・停止を追加。P0 で選定した方法で対象の repo と親を結び、既存の `managed-client.ts`、承認 UI、Worker ターミナルに接続。フォルダーなし・複数ルート・同じ repo の別ウィンドウも試験する。
- [ ] 開始の確認が必要な場合は開始元ウィンドウに「この範囲で開始」を表示し、追加権限の要求は同じウィンドウに通知する。通知から対象・理由・範囲差分を確認して許可または拒否でき、見逃した要求は Meristem の進捗表示から開けるようにする。開始と承認に PowerShell、`discovery.json` の手選択、ID の手入力、承認用コマンドの検索を要求しない。
- [ ] `scripts/package-extension.ps1` に配布 runtime の同梱と整合性検査を追加。拡張のユーザー用領域と run ごとの状態領域を使い、普段の Codex の設定や無関係なチャットへの影響を確認する。
- [ ] `ide` は `npm run test:terminal` と通常プロファイル相当の実機 V。`vsix` は `npm run package:extension`（新規出力）と、開発 checkout・別途配布した ZIP のない環境で VSIX のみから開始できること。初期導入・無効化・ユーザーが後編集した設定の保全を記録する。

### P5　公式 Codex CLI で使う

- [ ] `scripts/meristem.ps1` と `src/cli.ts` のユーザー向け入口で初回設定、開始、使用状況、状態、相談回答、停止を提供。P0 で選んだ公式 TUI 経路に接続する。ローカル人入力とモデル由来プロセスを照合する。CLI のみで認証済みの既定環境を利用し、パス・スレッド ID の手入力を通常操作から外す。
- [ ] `cli` は `npm run build` 後の `node --test dist/test/cli-parent.test.js` と実機 C。`cli-stop` は人の Ctrl+C、端末強制終了、同じ端末の別会話、同一 repo の2端末で停止・報告の対象を照合。Worker の終了確認、次回の明示再開、承認経路を通す。

### P6　v0.2.0 からの更新と v0.3.0 受入

- [ ] `verify` は `npm run verify`。旧版の専用プロファイルから新環境へ移る手順と、旧形式の保存状態を照合できることを試す。DB 追加移行があれば旧形式の保全・復元を試験し、ダウングレード条件を配布文書に書く。
- [ ] `acceptance` は仕様 V/C/Q/M。VS Code・CLI で同じ工程表を実行。低残量と回復は fixture、取得可能な窓と親の往復は実機で確認する。ビルド SHA、Codex 版、親と Worker の件数、最終 SHA、停止結果、未達項目を記録。チェックの失敗や未実施を成功扱いしない。
- [ ] 実機 V では、人の開始指示を照合できる場合の追加の開始確認が0回、確認が必要な場合は開始元の VS Code で1操作で開始できることを観測する。承認前に環境不備が表示されること、同じ範囲での再試行・通常のコミットと push で再承認が出ないこと、範囲拡張だけが同じウィンドウで通知され、許可と拒否が正しく反映されることを確認する。開始、再試行、通常作業、範囲拡張で要求された利用者の操作数を記録する。
- [ ] `package` は版番号を揃え、配布用 PowerShell で `./scripts/package-release.ps1 -OutputDirectory $newOutput -NodeExe $selectedNode -NodeLicensePath $nodeLicense -NodeChecksumsPath $nodeChecksums` を実行する。各変数は新しい出力先・検証済み Node 実体・対応ライセンス・公式 checksum ファイルの絶対パス。クリーン環境で VSIX / CLI ZIP の展開・起動・復元・hash を確認する。README 日英・導入手順・リリースノートに入口別の対応方式、残量表示、旧版からの移行を記載する。公開・タグ作成は受入後のリリース操作とする。
