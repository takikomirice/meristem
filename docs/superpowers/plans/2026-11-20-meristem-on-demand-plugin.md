# 普段の Codex チャットから必要なときだけ Meristem を使う実装計画

> 実装時は `superpowers:executing-plans` に沿って段階ごとに検証する。チェックは実測後に付ける。

**目標**　Meristem を一度インストールすると、普段の VS Code の公式 Codex サイドバーで「Meristem でこのファイルを確認して」と頼める。読み取り専用 Worker が1人動き、その結果が同じ親の応答に返る。使う前と終了後の Meristem 専用プロセスは0個にする。その後、「この計画を実装して」からの自動選択と編集へ広げる。

**構成**　プラグインには使いどころを説明する Skill と、必要時だけ起動するローカル CLI を同梱する。最初の往復は親のシェルツール呼び出しに結び付け、CLI の標準出力で結果を返す。呼び出しごとの Worker 管理は CLI の生存期間内で完結させる。

**対象**　Windows x64、公式 Codex、PowerShell、TypeScript、既存の WorkerRuntime と Windows Job。最初の受入は普段と同じ構成の公式サイドバーで行う。既存の管理ターミナルと単体 CLI は従来の入口として維持する。

**背景**　現在の MCP 設定は実行ごとに固定した名前付きパイプを指定する。専用プロファイルで既存のサイドバー会話から Worker を使えた実績はあるが、通常のサイドバーから単発 CLI を呼ぶ経路は未検証。P6 の配布・移行・下書き試験はそれぞれ既存の計画で追跡する。[現行の登録処理](../../../src/install.ts)・[P4 の実機結果](2026-11-19-meristem-v030.md#p4通常-vs-code-で使う)・[P6 前の検証記録](2026-11-20-meristem-pre-p6.md)

## 利用者から見た合格条件

**2026-11-21 の実装状況**　`inspect`、ローカルプラグイン配布、サイドバー A/B とモデル送信0回の試験用コマンドを追加した。`run` は版2の工程表を読み、依存関係・作業範囲・同時実行上限から初回の割当候補を返す。通常サイドバーでの権限確認を実証するまでは、編集・Git 保存を開始せず終了コード2を返す。[入口ごとの結果と一括受入手順](../../validation/chat-control/on-demand-sidebar.md)

| 場面 | 観測する結果 |
| --- | --- |
| 導入して雑談や小さな質問をする | Meristem のコマンド呼び出し0回。専用の MCP、relay、管理プロセス、Worker は起動しない。 |
| 「Meristem でこのファイルを確認して」と頼む | 工程表の右クリック、別ターミナルへの移動、スレッド ID の入力なし。元の会話にそのファイル固有の結果が返る。 |
| 分担できる計画について「実装して」と頼む | Codex が作業範囲と依存関係から Meristem を選べる。小さな変更は直接行える。選択の成否と理由を事例ごとに記録する。 |
| 完了・取消・アンインストール | 実行時に作ったプロセスが終了する。アンインストール後は新しい会話で Skill が読み込まれず、作業ファイル・コミット・既存の Codex 設定が保たれる。 |

## 1. 普段のサイドバーから単発コマンドを呼べるか確かめる

**成果物**　`test/live/on-demand-probe.ts` と、`docs/validation/chat-control/on-demand-sidebar.md` の入口別記録。ここで実装の可否を左右する二点を先に測る。

- [ ] 公式拡張と通常のサンドボックス設定を使い、Meristem VSIX、専用 relay、グローバル MCP 登録を必要としない状態を用意する。テスト用リポジトリのパスに空白を含める。
- [ ] 同じリポジトリでサイドバーの会話 A/B を開く。各会話から別の短い識別文字列を単発 CLI に渡し、呼び出し元の応答だけに対応する文字列と終了コードが返ることを確認する。親の識別にウィンドウ名、最新履歴、モデルが書いたスレッド ID を使わない。
- [ ] 同じ起動元から、既存の Worker host と読み取り専用 Codex を起動・終了できるか調べる。最初はモデル送信0回で、実行ファイル・認証・隔離・終了を個別に確認する。初回だけの許可と呼ぶたびに必要な許可を記録する。通常の権限で子プロセスや認証を利用できない場合は、拒否された操作を記録し、その時点で通常経路の成立判定を保留する。

実機観測には元の呼び出しの出力と終了記録を使う。観測のたびにサンドボックス外実行を求める手順は利用者の操作に組み込まない。別ターミナルを開けば通った場合は、その結果を別入口の参考記録として残す。

## 2. 読み取り専用 Worker 1人の結果を同じ応答に返す

**変更先**　新規 `src/on-demand.ts`、`test/on-demand.test.ts`。単発起動には [WorkerRuntime](../../../src/workers.ts)、[WorkerHost](../../../native/WorkerHost.cs)、[ProcessTree](../../../native/ProcessTree.cs) の既存の隔離・モデル確認・停止処理を利用する。

- [x] 最小の入口を `meristem inspect <リポジトリ内の相対ファイル>` とする。呼び出し元の作業ディレクトリから Git ルートを確定し、対象ファイルの実体を照合する。成功時は stdout に UTF-8 の JSON を1件だけ返す。例は `{"status":"completed","file":"src/example.ts","summary":"…"}`。エラーと取消は非ゼロ終了とし、秘密情報や会話の全文を出力しない。
- [x] 模擬 Codex でテストを先に作る。正常時は Worker 1人・指示1回、同じ Worker の完了ターンに属する結果1件、終了確認後にのみ成功とする。存在しないファイル、リポジトリ外を指す相対パスやジャンクションは起動前に拒否する。質問・承認待ちや配信結果不明を完了として扱わず、不明な指示を再送しない。
- [x] 単発 CLI から読み取り専用の担当を起動し、対象ファイルと調査目的を渡す。Worker の最終テキストを、自分が起動した attempt・thread・turn と照合して返す。Worker が返した文字列は調査結果として扱う。モデルによる開始許可の代行や、既存の人用 `start` の呼び出しは追加しない。
- [x] 取消、タイムアウト、親シェルの強制終了も模擬試験に含める。子孫プロセスまで終了したことを Job・PID・生成時刻で照合する。同じリポジトリで A/B が同時に実行しても、A の取消で B の Worker を終了させない。
- [ ] `npm run build:native`、`npm run build`、`node --test dist/test/on-demand.test.js dist/test/workers.test.js` を実行する。モデルを使う受入では、専用の小さなファイルに毎回異なる値を置き、親から値を教えずに Worker の結果が同じ応答へ返ることを確認する。実モデルの枠はこの試行用に決める。

## 3. プラグインとして追加・削除できるようにする

**変更先**　新規 `plugins/meristem/.codex-plugin/plugin.json` と `plugins/meristem/skills/meristem/SKILL.md`。配布物の組み立てと検査には [配布スクリプト](../../../scripts/package-release.ps1) と [パッケージ試験](../../../test/package.test.mjs) の部品を使う。

- [ ] サイドバーで利用可能なローカルプラグインの導入・削除手段を実機で確認し、対応版と操作を記録する。配布物に Skill、単発コマンドの起動スクリプト、必要なランタイムとライセンスを揃える。Skill はインストール先を基準にコマンドを解決する。開発 checkout、手動の PATH 編集、バックグラウンドサービス、Codex の `cliExecutable` 差し替えは導入条件に含めない。[プラグインのパッケージ仕様](https://developers.openai.com/plugins/build/plugins)
- [x] パッケージ試験を追加し、展開した配布物から `inspect` を起動する。既存の MCP 設定・VS Code 設定と共存できること、登録解除後も既存の設定とユーザーの成果が残ることを比較する。
- [ ] インストール → 通常の会話 → 明示指定による1往復 → アンインストールを通す。プロセス数はこの試行の実行パス・PID・子孫関係で数える。普段から動いている Codex や他の Node プロセスは集計から除く。ここまでを**明示指定できる初版**の受入とする。

## 4. 「実装して」から既存の分担・保存機能へつなぐ

**変更先**　`plugins/meristem/skills/meristem/SKILL.md`、`src/on-demand.ts`、[既存の工程表制御](../../../src/broker.ts)、`test/on-demand.test.ts`。1〜3の往復を確認してから着手する。

- [ ] 次の入口を `meristem run <工程表の相対パス>` とする。親チャットが作業中の工程表を渡し、既存の計画読取り・依存判定・同時実行上限・作業範囲を利用する。会話上にしか計画がない場合は、親が合意した内容から工程表を保存してから渡す。複数の候補を区別できない場合は対象を確認する。
- [ ] 編集・Git 保存に必要な権限は既存の開始範囲の確認と同等に保つ。`inspect` の成功を編集や push の許可に流用しない。通常サイドバーで利用者が許可範囲を確認できる経路を実証してから、編集を有効にする。結果不明や停止後の再試行で二重に割当・保存しないことを回帰試験に含める。
- [ ] Skill に明示指定と自動選択の例を書く。「Meristem で実装して」、独立した2件を含む「この計画を実装して」、1行の訂正、相談だけの4例で、明示指定の実行、分担の選択、直接編集、起動0件をそれぞれ観測する。模擬試験は選択後の動作を、実機試験はモデル自身の選択を記録する。
- [ ] ローカル bare Git を使い、並列2件 → 報告 → 保存・検証 → 監査 → 統合を元のサイドバーから完了する。最終 SHA、停止結果、他会話への結果混入0件を記録する。`npm run verify` と既存の CLI・VS Code の回帰結果を確認し、実証できた導入・削除・起動方法だけを README 日英に載せる。

## 自動再開の扱い

初版では、実行中の呼び出しを親が待ち、同じ応答内で結果を読む。長い処理でシェルツールが途中で制御を返す場合も、元の呼び出しの完了を同じ応答中に待てるかを実測する。親の応答終了後に Worker の完了で新しいターンを始める機能は別の受入とする。そこでは**同じ試行・同じ会話**で、未送信の下書きの前後一致、自動通知1回、その後の人の送信1回、別会話への配送0件を確認する。[下書き試験の既存記録](2026-11-20-meristem-pre-p6.md)
