# Meristem v0.3.0 仕様案

2026-11-19。Windows x64 の v0.2.0（`befafa89ddeb22043155868c340912da9cef3802`）を基準とし、[実装計画](../plans/2026-11-19-meristem-v030.md) の実機受入を通した構成を v0.3.0 として配布する。

## 利用者の操作

| 入口 | 起動から作業完了まで |
|---|---|
| 普段の VS Code | 通常プロファイルに VSIX を一度導入する。開いているリポジトリで公式 Codex チャットから Meristem を呼ぶ、または拡張コマンドで開始する。対象の工程表・親・ブランチ・権限を確認する。同じウィンドウで指示、進捗、相談回答、停止ができ、別ウィンドウや設定 JSON の手編集を要求しない。 |
| 普段のターミナル | 公式 Codex CLI の対話セッションを親にする。Meristem の MCP ツールを呼ぶか、管理対象の公式 TUI を端末で起動する。人はローカルの管理コマンドで対象確認・承認・相談回答・停止ができる。VS Code を終了した状態で、Worker の報告を受けた親が次の工程まで進める。 |
| 使用状況 | 両方の入口から、対象アカウントの Codex 利用枠ごとの使用済み％、残り％、リセット予定、最終取得時刻を表示する。現在の Worker 数、希望人数、人が承認した上限、残量による上限、最終的な上限と理由を同じ情報源から表示する。 |

Coordinator は人が指示する親の Codex 会話、Worker は独立した履歴・作業場所を持つ Codex CLI チャット。利用者のサブスク認証で起動する。利用枠計測のための推論ターンは使わない。

## どの会話を親にするか

| 方式 | 利用者にとっての利点・負担 | 実装難度と判定項目 |
|---|---|---|
| 開いている公式会話をその場で親にする | 相談して決めた前提、履歴、モデル選択を引き継げる。会話中に必要なときだけ分担を頼める。 | 高。呼出元の親とターンを検証し、終了後に同じ会話へ一度だけ報告を戻し、手入力や停止と競合しないことを入口ごとに実証する。MCP ツールを呼べることは最初の一方向だけの証明。 |
| 同じウィンドウ・端末で新しい親を開く | 対象リポジトリと親が明確で、停止・再開を追跡しやすい。工程表や人が選択した指示を引き継ぐ一手間がある。 | 中。親生成時の ID と制御接続を所有できる。VS Code 側には親の入出力・承認表示、CLI 側には公式 TUI の接続と切断処理が要る。 |

**親は、その run で最初に Meristem を開始した公式 Codex の会話とする。** 通常の会話で呼び出した場合はその履歴を引き継ぎ、親の選択画面を出さない。ターミナルでは、そこで対話中の Codex スレッドを結び付ける。同じ端末で別スレッドに切り替えても親は移らない。ツールの一覧表示や使用状況の照会は開始操作に含めない。開始要求の再送は元の run に対応付け、別会話からの同一 run の取得要求は拒否する。

実装方式は実機検証で選ぶ。VS Code と CLI でそれぞれ両案を試し、親の識別、報告後の自動再開、停止、別会話との分離を比較する。既存会話で全て成立する入口はそこから開始する。管理起動だけが合格した入口では「新しい公式 Codex セッションで開始」のように区別し、元の会話から自動で切り替えない。元の会話を親にできたかを入口ごとにリリース判定に記録し、代替だけで出すかは利用者と決定する。両案未達なら再設計する。

## 接続と実行の契約

v0.2.0 は親の thread ID と relay の pipe を導入時に固定し、拡張が保持する管理接続の喪失で run を止める。親認証は所有プロセス・世代・実際に観測した thread/turn を照合する。これを起動単位に組み立て、親の種類、所有プロセス、セッション ID、run、repo、工程表を一意に対応させる。Worker の割当・報告・Git 統合は既存の broker、SQLite、MCP を通す。[設定生成](../../../src/install.ts)・[親照合](../../../native/StdioRelay.cs)・[管理接続](../../../src/cli.ts)

- VS Code の通常プロファイルに公式拡張の CLI 差し替えを常設する方式は採用前に影響を評価する。製品の合格条件は、同時に開いた無関係なチャット・ウィンドウが通常通り動くこと。Meristem が追加する設定の範囲を提示し、無効化・削除で利用者の後編集を保護する。
- Windows x64 用 VSIX は v0.2.0 ZIP に含まれる Node、管理用 native バイナリ、JS、SQL、依存・ライセンスを同梱する。Git と対応する公式 Codex は初回診断で案内する。CLI 単体配布にも同じエンジンを同梱する。開発 checkout・旧 ZIP を持たない環境で試す。
- CLI は公式 TUI が MCP を呼ぶ構成を実証する。管理起動の候補はローカルで所有する App Server と公式 TUI の `codex --remote`。固定版のヘルプにオプションがある。複数クライアントによる同一 thread の表示・再開、停止通知、所有者識別は別々に試す。ローカル接続にはユーザー限定のアクセス制御または起動単位の認証を用いる。
- 人の許可には対象の run・repo・plan・親を表示する。CLI は人が直接開いた制御経路で本人の入力を受け、モデルのシェルや MCP 呼出しとの識別を実証する。識別不能なら保留する。モデル申告の ID、最新チャット、アクティブなタブだけに基づく割当を拒否する。
- Worker の報告と正常なターン終了を記録した後、既存の wake 条件と重複防止を使う。親の実行中ターンとは競合させず、人の未送信の下書きを保持する。下書き入力を検出できるかは実機試験で記録し、ターンが idle という情報だけで人の入力状態を推定しない。停止・切断では新規配送を止める。CLI では TUI の終了や親の制御接続喪失を VS Code の管理接続喪失に対応させる。Ctrl+C のターン中断とプロセス終了を区別し、結果不明時は照合後に明示再開する。

## サブスク残量と並列数

対象はログイン中の ChatGPT アカウントに割り当てられた **Codex の時間窓ごとの枠**。固定版 `0.169.0-alpha.11.1` の生成型で `account/rateLimits/read`、`account/rateLimits/updated`、`usedPercent`、`resetsAt` を確認した。使用割合とリセット時刻が実際に返る範囲はプランや応答による。料金・トークン数からの推定は行わない。[公式 App Server 仕様](https://learn.chatgpt.com/docs/app-server)・[公式 CLI / IDE の MCP 設定](https://developers.openai.com/learn/docs-mcp)

1. 親と Worker の課金先が一致することを認証コンテキストで確認する。起動時・手動更新・期限切れで公式応答を読み、更新通知は再取得の契機とする。同時の取得をまとめ、遅れた旧応答を捨てる。アカウント変更・再起動で再取得する。保存・画面表示は判定に必要な値に絞る。
2. `rateLimitsByLimitId` から当該実行が使う Codex 枠を選び、旧形式は照合できた単一の `rateLimits` を使う。無関係なモデル枠やクレジットは合算しない。対象枠の有効な primary / secondary それぞれについて `残り％ = 100 − usedPercent`。片方が正式に null のときは存在する窓を使い、両方あるときは小さい残り％で制御する。窓名は取得した期間を使い、時刻は Unix 秒から利用者の現地時刻に変換する。
3. 新規 run 向けの初期案は「残り20％以下なら同時 Worker を1人まで、残り0％なら新規割当を待機」。20％超は既存の上限。人が run 開始前に低残量のしきい値と制限人数を設定、または自動制限を無効化できる。しきい値は整数1〜99、人数は正整数。旧 run に設定がない場合は既存の並列数を採用。サーバーが利用不可を明示した場合は自動制限の設定にかかわらず待機する。
4. 計測値の有効期間は初期案60秒。次の reset が先ならその時点で再取得する。期間や reset だけが null なら「不明」と表示し、有効な％を使う。未対応、タイムアウト、無効値、対象枠不明、古い値は「取得不能」または「更新待ち」。自動制限中は新規枠を最大1人に絞る。直前に枯渇・利用不可を確認していた場合は上限0を保持する。`ordinaryUsageAllowed: false` の後に null や正の残量が届いても拒否を解除しない。同一アカウントの新しい true と有効な残量で再評価する。時計が reset を過ぎただけでは増員しない。
5. run ごとの実効上限は工程表の希望数、人の承認上限、残量上限の最小値。対象は同時 Worker 数。親の人数は含めない。判定は予約直前の単一 writer のトランザクションで行い、予約〜終了確認までを数える。枠が下がった時点で走っている Worker は報告・終了まで進める。例として稼働3人のとき上限1になれば、稼働が0人になるまで次を割り当てない。引継ぎ・再試行・保留解除後の新規割当も同じ経路を通す。
6. 制限で待つタスクは失敗回数を消費せず、待機理由を表示する。状態照会・停止・報告・人の相談回答は利用可能。回復確認時は既存の依存・承認を再評価し、親へ一度だけ通知する。無制限の再試行や待機中のモデル呼出しは行わない。同一アカウントの他セッションの消費は公式値の更新で反映する。v0.3.0 の人数上限は各 run に適用し、複数 PC・複数 run 合算の人数保証は対象外。
